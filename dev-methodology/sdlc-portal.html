축 A · 진행 순서

생명주기 모델

요구분석부터 유지보수까지의 단계를 어떤 순서와 흐름으로 밟을지 정합니다. 한 번에 순서대로 가는 순차형과, 여러 번 돌며 키워 가는 반복형으로 나뉩니다.

폭포수 모델

Waterfall · 순차형
1970

각 단계를 순서대로 끝내고 다음 단계로 넘어갑니다. 이전 단계로 되돌아가는 일은 원칙적으로 피합니다.

장점
관리가 쉽고 산출물이 명확함
단점
요구 변경에 취약, 결과물을 늦게 확인
적합
공공·국방 SI, 고정 범위 계약

V-모델

V-Model · 순차형
1980s

폭포수의 왼쪽 개발 단계마다 오른쪽 검증 단계를 짝지어, 무엇을 기준으로 테스트할지 처음부터 정합니다.

장점
검증 기준이 명확, 추적성 높음
단점
폭포수와 같은 경직성
적합
의료기기, 자동차(ISO 26262), 항공

프로토타입 모델

Prototyping
1980s

빠르게 시제품을 만들어 사용자에게 보여 주고, 피드백으로 요구사항을 다듬은 뒤 본 개발에 들어갑니다. 버리는 시제품과 발전시키는 시제품이 있습니다.

장점
요구 오해 감소, 사용자 참여
단점
시제품을 완제품으로 오인할 위험
적합
UI 중심, 요구사항이 불분명할 때
사용자 피드백요구 구체화

나선형 모델

Spiral · 반복형
1986

계획 → 위험 분석 → 개발·검증 → 고객 평가의 네 사분면을 여러 번 돌면서 점점 완성도를 높입니다. 매 회전마다 가장 큰 위험부터 해소합니다.

장점
위험 관리 중심, 대형 시스템에 유리
단점
위험 분석 전문성 필요, 관리 복잡
적합
대규모·고위험 프로젝트
위험 주도Barry Boehm

반복적·점진적 모델

Iterative & Incremental
1990s

시스템을 여러 조각으로 나눠 조금씩 완성해 나갑니다. 점진적은 기능을 하나씩 더하는 방식, 반복적은 전체를 여러 번 다듬는 방식입니다.

장점
일찍 작동하는 버전 확보, 위험 분산
단점
초기 아키텍처가 약하면 재작업
대표
RUP, 애자일의 바탕

1990s

제품 계열 방법론

Product Line Engineering
2000s

비슷한 제품군의 공통 기능을 핵심 자산으로 만들어 두고, 제품마다 다른 부분만 더해 개발합니다. 임베디드나 가전 제품군에 많이 씁니다.

중심
공통 핵심 자산

애자일 상세

개인과 상호작용프로세스와 도구보다

XP

eXtreme Programming
1999

좋은 개발 습관을 극단까지 실천합니다. 관리 틀보다 엔지니어링 실천법이 중심이라 스크럼과 함께 쓰는 경우가 많습니다.

2007

지표

적합

DevOps

Development + Operations
2009

개발과 운영의 벽을 없애고 자동화로 빠르고 안정적인 배포를 반복합니다.

실천

지표
DORA: 배포 빈도, 변경 리드 타임, 변경 실패율, 복구 시간

DevSecOps

Security as Code
2010s

보안을 마지막 점검이 아니라 파이프라인 전 단계에 넣습니다(Shift-left). 정적 분석, 의존성 취약점 검사, 비밀정보 탐지를 자동화합니다.

자주 반복되는 설계 문제에 이름을 붙인 검증된 해법입니다. 진행 순서(축 A)나 설계 관점(축 B)과 달리, 클래스와 객체를 실제로 어떻게 짤지를 다룹니다. 주로 객체지향으로 설계할 때 씁니다.

생명주기 모델언제, 어떤 순서로 진행할까폭포수, 반복적
개발 방법론무엇을 중심으로 설계할까객체지향, CBD
아키텍처 패턴시스템 전체를 어떤 구조로 나눌까계층형, MVC
디자인 패턴클래스와 객체를 어떻게 짤까전략, 옵저버

이런 문제가 있을 때 코드에서 자주 만나는 상황부터 찾아보세요

문제 상황패턴실무 예
외부 라이브러리나 API의 인터페이스가 우리 코드와 맞지 않는다어댑터여러 결제 PG사 SDK를 하나의 결제 인터페이스로 감싸기
if/switch로 알고리즘이나 정책을 골라 쓰고, 경우가 계속 늘어난다전략회원 등급별 할인 정책, 로그인 방식(카카오·구글·이메일)
상태에 따라 같은 메서드의 동작이 달라지고 분기가 복잡하다상태주문 상태: 결제 대기 → 배송 중 → 완료 → 환불
한 객체가 바뀌면 여러 곳이 알아야 한다옵저버이벤트 리스너, 상태 관리 라이브러리의 구독
생성자 인자가 너무 많고 선택 항목이 많다빌더HTTP 요청, SQL 쿼리 빌더
기존 클래스를 고치지 않고 기능을 덧붙이고 싶다데코레이터로깅·캐시·재시도를 감싸는 래퍼
여러 하위 시스템을 호출하는 순서가 복잡하다퍼사드주문 서비스 하나가 재고·결제·배송을 대신 호출
실행 취소와 다시 실행이 필요하다커맨드 + 메멘토에디터의 Ctrl+Z, 작업 이력
무거운 객체를 필요할 때만 만들거나 접근을 제어하고 싶다프록시ORM 지연 로딩, 권한 검사, 캐시
폴더와 파일처럼 부분과 전체를 같은 방식으로 다뤄야 한다컴포지트UI 컴포넌트 트리, 메뉴, 조직도
요청을 여러 단계가 차례로 검사하고 처리한다책임 연쇄웹 프레임워크 미들웨어(인증 → 로깅 → 처리)
어떤 구현 객체를 만들지 실행 시점에 정해야 한다팩토리 메서드알림 채널(문자·메일·푸시)별 발송기 생성

아키텍처 패턴 시스템 전체의 큰 구조

SOLID 원칙 기출 패턴의 바탕이 되는 객체지향 설계 원칙

S단일 책임클래스가 바뀌는 이유는 하나여야 합니다. 예: 주문 계산과 이메일 발송을 한 클래스에 두지 않기
O개방·폐쇄새 기능은 코드를 추가해서 넣고, 기존 코드는 고치지 않습니다. 예: 할인 정책을 전략으로 추가
L리스코프 치환하위 타입은 상위 타입 자리에 넣어도 똑같이 동작해야 합니다. 예: 정사각형-직사각형 문제
I인터페이스 분리쓰지 않는 메서드에 의존하지 않도록 인터페이스를 작게 나눕니다
D의존 역전구체 클래스가 아니라 인터페이스에 의존합니다. 의존성 주입(DI)의 바탕입니다
패턴은 문제가 생긴 뒤에 꺼내 쓰세요패턴을 먼저 정하고 코드를 맞추면 클래스만 늘어납니다. 같은 수정을 여러 곳에서 반복하거나 분기가 계속 늘어날 때, 해당 문제에 맞는 패턴을 적용하는 편이 낫습니다.
언어가 이미 패턴을 품고 있기도 합니다함수를 값으로 넘길 수 있는 언어에서는 전략·커맨드를 함수 하나로, 반복자는 for…of로, 옵저버는 이벤트 시스템으로 대신하는 경우가 많습니다.

    리드 타임 / 사이클 타임요청이 들어온 때부터 완료까지작업을 시작한 때부터 완료까지
    영역공학 / 응용공학제품군의 공통 핵심 자산 개발핵심 자산으로 개별 제품 개발
    응집도 / 결합도모듈 안의 관련성. 높을수록 좋음모듈 사이의 의존성. 낮을수록 좋음
    팩토리 메서드 / 추상 팩토리객체 하나의 생성을 하위 클래스에 맡김서로 어울리는 객체군을 한꺼번에 생성
    데코레이터 / 프록시감싸서 기능을 덧붙임감싸서 접근을 제어함
    전략 / 상태바깥에서 알고리즘을 골라 끼움내부 상태가 바뀌면 행동이 저절로 바뀜
    어댑터 / 퍼사드인터페이스 하나를 다른 모양으로 변환여러 하위 시스템 앞에 단순한 창구

    애자일 선언 4가치
    1. 프로세스·도구보다 개인과 상호작용
    2. 포괄적 문서보다 작동하는 소프트웨어
    3. 계약 협상보다 고객과의 협력
    4. 계획을 따르기보다 변화에 대응
    XP 핵심 가치5

    의사소통, 단순성, 피드백, 용기, 존중

    스크럼 구성
    • 역할: 제품 책임자(PO), 스크럼 마스터, 개발자
    • 이벤트: 스프린트, 스프린트 계획, 데일리 스크럼, 스프린트 리뷰, 회고
    • 산출물: 제품 백로그, 스프린트 백로그, 증분
    린 7원칙

    낭비 제거, 품질 내재화, 지식 창출, 결정 지연, 빠른 인도, 사람 존중, 전체 최적화

    단계 순서
    • 나선형: 계획 수립 → 위험 분석 → 개발·검증 → 고객 평가
    • RUP: 도입 → 정련 → 구축 → 전이
    • 폭포수: 요구분석 → 설계 → 구현 → 테스트 → 유지보수

    SOLID
