무엇을 · 성격

요구사항 종류

요구는 성격(기능/비기능)과 쓰는 수준(사용자/시스템)으로 나눕니다. 비기능은 다시 품질 특성으로 쪼개서 숫자로 확인할 수 있게 씁니다.

기능 요구사항 기출

Functional
무엇을

시스템이 무엇을 하는가입니다. 입력, 처리, 출력, 저장 같은 동작으로 씁니다.

예
회원은 이메일로 가입할 수 있다. 주문하면 확인 메일을 보낸다.
확인
된다 / 안 된다로 테스트

비기능 요구사항 기출

Non-functional
얼마나 잘

기능을 얼마나 잘 하는가입니다. 성능, 보안, 가용성, 사용성 같은 제약과 품질입니다.

예
검색 결과는 2초 안에 보인다. 동시 접속 1만 명을 견딘다.
주의
"빠르게"처럼 쓰면 검증할 수 없음. 숫자로 쓴다

사용자 요구사항 기출

User Requirements
고객 언어

사용자가 이해하는 말과 그림으로 쓴 요구입니다. 무엇을 원하는지를 넓게 담습니다.

예
지난달 주문 내역을 다시 볼 수 있어야 한다.
읽는 사람
고객, 기획자, 관리자

시스템 요구사항 기출

System Requirements
개발 언어

사용자 요구를 개발자가 구현할 수 있게 자세히 풀어 쓴 요구입니다.

예
주문 목록 API는 최근 12개월을 페이지당 20건으로 반환한다.
읽는 사람
개발자, 설계자, 테스터

인터뷰 기출

Interview

이해관계자와 직접 묻고 답합니다. 가장 기본이고, 숨은 사정을 듣기 좋습니다.

요령
열린 질문으로 시작, 끝에 요약해서 되묻기

브레인스토밍 기출

Brainstorming

여럿이 비판 없이 아이디어를 쏟아낸 뒤 묶습니다. 새 서비스 기획에 좋습니다.

요령
평가는 나중에, 양을 먼저

워크숍 (JAD) 기출

Joint Application Design

사용자와 개발자가 한자리에 모여 집중적으로 요구를 정합니다. 부서 간 충돌을 빨리 풉니다.

요령
진행자 지정, 결정 사항은 그 자리에서 기록

관찰 기출

Observation

사용자가 실제로 일하는 모습을 봅니다. 말로는 안 나오는 습관과 우회 방법을 찾습니다.

요령
묻기 전에 먼저 보고, 나중에 이유를 묻기

설문 기출

Questionnaire

많은 사람에게 같은 질문을 던져 경향을 봅니다. 깊이는 얕지만 범위가 넓습니다.

요령
인터뷰로 가설을 세운 뒤 설문으로 확인

프로토타이핑 기출

Prototyping

화면 시제품을 보여 주고 반응을 듣습니다. "보면 알 것 같다"는 요구에 가장 효과적입니다.

요령
시제품이 무엇을 검증하는지 먼저 알리기

유스케이스 기출

Use Case

사용자(액터)가 시스템으로 목표를 이루는 과정을 시나리오로 씁니다. UML 유스케이스 다이어그램으로 그립니다.

요령
정상 흐름 다음에 예외 흐름을 꼭 쓰기

분류와 충돌 해결

Classification

모은 요구를 기능/비기능, 우선순위, 담당 영역으로 나누고, 서로 부딪치는 요구를 조율합니다.

예
"모든 기록 보관" vs "개인정보 1년 후 삭제"

Modeling

도구
유스케이스, 활동 다이어그램, DFD, ERD

우선순위

MoSCoW · Kano

다 할 수 없으니 순서를 정합니다. MoSCoW는 꼭·되도록·가능하면·이번엔 안 함으로 나눕니다.

요령
Must가 절반을 넘으면 우선순위가 아님

타당성 검토

Feasibility

기술, 비용, 일정, 법적으로 가능한지 따집니다. 안 되는 요구는 이 단계에서 걸러야 쌉니다.

3 명세 Specification · 문서로 약속한다

요구사항 명세서 (SRS) 기출

IEEE 830 · ISO/IEC/IEEE 29148

요구를 빠짐없이 정리한 공식 문서입니다. 개발, 테스트, 계약의 기준이 됩니다.

목차 예
개요, 전체 설명, 기능 요구, 비기능 요구, 인터페이스

정형 명세 기출

Formal Specification

수학 기호와 논리로 씁니다. 모호함이 없지만 읽고 쓰기 어렵습니다.

예
Z, VDM, 페트리넷, 상태 기계
쓰는 곳
철도·항공 같은 안전 중심 시스템

비정형 명세 기출

Informal Specification

자연어, 표, 다이어그램으로 씁니다. 누구나 읽지만 해석이 갈릴 수 있습니다.

예
자연어 문서, 유스케이스, 유저 스토리

4 확인과 관리 Validation · 맞는지 검토하고 지킨다

동료 검토 기출

Peer Review

작성자가 동료에게 명세를 설명하고 결함을 찾습니다. 가볍고 자주 할 수 있습니다.

워크스루 기출

Walk-through

검토 자료를 미리 나눠 주고 짧게 회의하며 훑어봅니다. 비공식이고 오류 발견이 목적입니다.

인스펙션 기출

Inspection

훈련된 검토자들이 역할(진행자, 기록자 등)을 나눠 체크리스트로 꼼꼼히 봅니다. 가장 공식적입니다.

순서
계획 → 사전 교육 → 준비 → 회의 → 수정 → 후속 조치

추적 매트릭스 기출

Requirements Traceability Matrix

요구 하나하나를 설계, 코드, 테스트와 표로 잇습니다. 빠진 구현과 영향 범위를 바로 찾습니다.

베이스라인과 변경 관리 기출

Baseline · CCB

확정된 요구를 기준선으로 묶고, 바꿀 때는 변경 요청 → 영향 분석 → 승인(변경 통제 위원회) → 반영 순서를 따릅니다.

실무 · 애자일 팀

실무 도구

애자일 팀은 두꺼운 명세서 대신 짧은 스토리와 수락 기준으로 요구를 다룹니다. 단계는 같고 크기와 주기가 작아진 것입니다.

유저 스토리

User Story

누가, 무엇을, 왜 원하는지 한 문장으로 씁니다.

형식
[사용자]로서, [기능]을 원한다. [가치]를 얻기 위해.
예
구매자로서, 지난 주문을 다시 담고 싶다. 같은 물건을 빨리 사기 위해.

수락 기준

Given-When-Then

스토리가 끝났다고 볼 조건을 시나리오로 씁니다. 그대로 자동 테스트가 되기도 합니다(BDD).

예
주문 내역이 있을 때(Given) 다시 담기를 누르면(When) 같은 상품이 장바구니에 담긴다(Then).
